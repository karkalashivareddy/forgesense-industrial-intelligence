# Model & UI Provenance

What each number in the console is, who produced it, and what it does not mean.

This document exists because a portfolio demo that blurs the line between a
simulation and reality is worse than useless — it is misleading.

---

## 1. The single most important fact

> **ForgeSense renders synthetic telemetry generated by a simulator in this
> repository. It does not monitor, represent, or control any physical machine,
> and the models were trained on data generated by that same simulator.**

This is stated in the sign-in gate, the status strip, the Command Center
banner, the Scenario Lab, the Predictions limitations panel, and the System
provenance panel.

---

## 2. The data path, end to end

```
config/machine_profiles.json          ← authored synthetic profiles
        │
        ▼
simulator/telemetry_feed.py           ← generates readings (~5 s interval)
        │
        ▼
Kafka topic forge.telemetry.raw      ← transport (docker profile)
        │
        ▼
backend TelemetryValidator            ← rejects out-of-contract samples
backend TelemetryNormalizer           ← canonicalises
        │
        ▼
ML service POST /assess              ← anomaly score, failure risk, RUL, factors
        │
        ▼
backend DecisionEngine               ← intent → state machine → alert → work order
        │
        ▼
PostgreSQL + WebSocket               ← snapshot REST + STOMP deltas
        │
        ▼
ForgeSense console
```

Every arrow crosses a contract documented in `docs/API_FRONTEND_CONTRACT.md`.

## 3. Metric provenance

| Metric | Producer | Basis | Unit | What it is not |
| --- | --- | --- | --- | --- |
| Temperature, vibration, RPM, torque, pressure, current, voltage, power, flow, frequency | Simulator | `SYNTHETIC` | per `SensorType` | a measurement from real instrumentation |
| Health score (0–100) | ML service | `PREDICTED` | points | a certified condition rating |
| Failure risk (0–1) | ML service, GradientBoosting | `PREDICTED` | probability | a measured likelihood of a real failure |
| Anomaly score (0–1) | ML service, IsolationForest | `PREDICTED` | score | a confirmed fault |
| Estimated remaining | ML service regressor | `SYNTHETIC` | **simulator degradation steps** | hours, days, or calibrated RUL |
| Top drivers | Baseline perturbation | `PREDICTED` | signed probability delta | a percentage, or a SHAP value |
| Asset counts, alert counts, event counts | Backend | `OBSERVED` / `DERIVED` | counts | — |
| Fleet health average | Backend | `DERIVED` | points 0–100 | — |
| Production efficiency | Backend | `DERIVED` (modelled) | % | measured throughput |
| Estimated downtime risk | Backend | `DERIVED` (modelled) | minutes | realised downtime |
| Scenario impact | ImpactEngine | `SIMULATED` | minutes, units | an outcome that occurred |
| WebSocket connections | Backend | `OBSERVED` | count | — |

## 4. The models

From `ml-service/models/model-metadata.json` and `/health`:

| Model | Version | Purpose |
| --- | --- | --- |
| Failure risk | `failure-risk-v2` | GradientBoosting classifier → probability |
| Anomaly | `anomaly-model-v2` | IsolationForest → novelty score |

Reported evaluation figures, **held-out metrics on generated data**:

| Metric | Value |
| --- | --- |
| Anomaly AUC | 0.8859 |
| Risk AUC | 0.9978 |
| RUL RMSE | 27.18 **steps** |
| Protocol | 20% held-out random split, seed 7 |

> These numbers describe how the models performed on data drawn from the same
> synthetic generator they were trained on. They are **not** a claim about
> accuracy on real industrial equipment, and the console never presents them as
> such — the ML service is read through the backend, and only the model
> *version* is surfaced.

`feature_schema_version: instantaneous-zscore-v1` — the feature vector is an
instantaneous z-score against the training distribution.
`training_data_version: synthetic-generator-v2` — the training data is generated.

## 5. Attribution — what it is and is not

**Method: local baseline perturbation.** For each active sensor, the value is
replaced with its training-set average, one at a time, and the change in model
output is attributed to that sensor.

- O(F) model evaluations — cheap enough for real-time inference.
- Deterministic, local, first-order.
- Does **not** capture feature interactions.

It is **not SHAP**. No SHAP library is used and none of the SHAP axioms hold.
The source file states this explicitly and the Predictions workspace repeats it
on every attribution panel, because calling this "SHAP" would be a
category error that a technical reviewer would catch immediately.

`contribution` is a **signed change in model output probability**. It is
rendered without a percent sign. An earlier backend build rendered it as
`label (+X%)`, which produced literal text like `NEUTRAL (+-2%)` for a negative
contribution; that is fixed and pinned by
`DecisionEngineFormattingTest`.

## 6. Remaining useful life

`rulUnit` is `steps` and only `steps` — the simulator's degradation horizon
(`rul_horizon_steps: 60`).

- Displayed as **"Est. remaining — 60 steps"**.
- The frontend contains **no** hours/days/minutes RUL formatter, and a unit
  test asserts the output cannot match a time unit.
- The Predictions limitations panel states plainly that it is not hours, days,
  or a calibrated remaining-useful-life.

---

## 7. The simulation boundary

`POST /api/v1/simulation/run` injects a fault into the **synthetic generator**.

- It changes what the simulator emits next.
- It does not connect to, command, or model any physical asset.
- Its outputs (downtime, throughput loss, production loss) are computed from
  per-edge propagation factors and per-machine throughput — **modelled
  assumptions**, and the backend ships its own `dataLabel` and `assumptionsJson`
  which the console renders verbatim.

The Scenario Lab states "SIMULATION MODE — NO PHYSICAL MACHINE CONTROL" above
the run controls, not in a tooltip.

## 8. What would change for production

1. **Ingest.** Swap the simulator for a real broker client (OPC UA, MQTT) and
   keep the `TelemetrySample` contract. The validator, normalizer and pipeline
   are already transport-agnostic.
2. **Identity.** Replace the shared `FORGESENSE_DEV_PASSWORD` with an OIDC /
   SAML provider. The backend's role checks already sit behind Spring Security,
   so the console's role gating stays valid.
3. **Storage.** Add a time-series store alongside PostgreSQL; the telemetry
   endpoint already takes a `limit` and a range.
4. **Model lifecycle.** Move to a model registry with drift monitoring and
   per-model evaluation gates. The metadata already carries a version and an
   artifact hash.
5. **RUL.** Retrain against real failure data and a validated time unit, then
   — and only then — change the unit contract. The UI would need a new
   formatter and the existing test deliberately forbids a time unit.
6. **Provenance.** `demoMode` would become a deployment property, and
   `dataBasis` would be derived from the ingest source rather than a flag.
