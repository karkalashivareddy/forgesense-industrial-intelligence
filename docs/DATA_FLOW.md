# ForgeSense — Data Flow

> **Scope note.** Rewritten during release packaging. The previous version
> claimed the browser transport was REST polling and referenced
> `frontend/js/app.js` (deleted in the React re-architecture) and
> `/api/v1/machines/{id}/telemetry/range` as the endpoint the UI calls. The UI
> actually calls `/api/v1/machines/{id}/telemetry?limit=N` and receives STOMP
> deltas over WebSocket. Corrected below.

---

## 0. The one thing a reviewer must not confuse

> **Every operational value in ForgeSense is synthetic.**
>
> It is generated by a Python simulator, scored by a model trained on that
> simulator, and displayed in an operations console. ForgeSense **does not
> observe, monitor, or actuate physical machinery.** There is no OPC-UA client,
> no MQTT client, no fieldbus driver, and no write path to any device. The
> machine bodies in the 3D twin are **representative geometry, not surveyed
> plant models**, as the twin's own caption states.

If a number on screen could be mistaken for a measurement of a real asset, it
is a defect. See the provenance table in §3.

## 1. The complete scenario flow (verified end to end)

This is the demo spine, with the **actual** endpoint and event names. Every
arrow below was executed against the running system; the observed numbers are
quoted in `DEMO_RUNBOOK.md`.

```text
  Scenario Lab (UI)
        │  operator picks VIBRATION_SPIKE, severity 0.9, asset M-104
        ▼
  POST /api/v1/simulation/control        { machineId, scenario, severity }
        │
        ▼
  Backend  ──forge.simulation.commands──►  Simulator changes its output
        │
        │  simulator now emits elevated vibration for M-104
        ▼
  POST /api/v1/telemetry/ingest          (bearer token)
        │
        ▼
  forge.telemetry.raw ──► forge.telemetry.normalized
        │
        ▼
  validate + normalize   (staleness ≤ 60 s, physical range checks)
        │
        ▼
  Digital twin state  ── the authoritative machine record
        │
        ├────────────► ML service  POST /assess  (feature vector)
        │                     │
        │                     └─► anomalyScore, anomalyLabel, failureRisk,
        │                         rulEstimate, factors
        │
        ▼
  Decision engine (rules in application.yml — not ML policy)
        │
        ├─► state machine:  NORMAL → DEGRADED → WARNING → CRITICAL
        ├─► impact engine:  dependency/line propagation, downtime estimate
        ├─► alert lifecycle:  NEW → ACKNOWLEDGED → INVESTIGATING → RESOLVED
        └─► maintenance:  RECOMMENDED → SCHEDULED → ACTIVE → COMPLETED | CANCELLED
        │
        ▼
  Broadcast over WebSocket  /ws   →   /topic/**   (13 topics)
        │
        ├─ telemetry.updated · machine.updated · machine.state.changed
        ├─ prediction.updated
        ├─ alert.created / alert.updated
        ├─ maintenance.created / maintenance.updated
        └─ impact.updated · simulation.* · events.updated
        │

        → ONE dispatch per animation frame
        │
        ├─► useTelemetryStore   (live sensor values, bounded ring, watched only)
```

## 2. Operator actions (the only write paths)

| Action | Endpoint | Effect |
|---|---|---|
| Acknowledge alert | `POST /api/v1/alerts/{id}/acknowledge` | lifecycle only |
| Investigate alert | `POST /api/v1/alerts/{id}/investigate` | lifecycle only |
| Resolve alert | `POST /api/v1/alerts/{id}/resolve` | lifecycle only |
| Schedule / start / complete / cancel work order | `POST /api/v1/maintenance/{id}/{action}` | advances the 5-state workflow |
| **What-if analysis** | `POST /api/v1/simulation/run` | **computes modelled impact; changes nothing** |
| **Inject into live feed** | `POST /api/v1/simulation/control` | **changes what the simulator emits** |
| Clear injection | `POST /api/v1/simulation/control/{machineId}/clear` | removes the injected scenario |
| Pause / resume / reset simulator | `POST /api/v1/simulation/{pause,resume,reset}` | simulator-level |

**None of these touch physical equipment.** "Inject" means *change the synthetic
generator's parameters*. The console labels these two actions separately for
exactly that reason, and `ScenarioType` is an explicit backend enum:

`NONE · DEGRADATION · OVERHEATING · BEARING_FAILURE · VIBRATION_SPIKE ·
RPM_INSTABILITY · CURRENT_SPIKE · SENSOR_FAILURE · MACHINE_OFFLINE ·
LOAD_INCREASE · MAINTENANCE · RECOVERY`

## 3. Data provenance — the honesty vocabulary

The console labels every significant value with one of these. The vocabulary
lives in `src/domain/basis.ts` and is unit-tested in `test/basis.test.ts`.

| Label | Meaning | Example on screen |
|---|---|---|
| **OBSERVED** | A value reported by the backend for this deployment. Still synthetic in *content*, because the deployment simulates a plant. | Assets, health score, sensor values, connectivity |
| **DERIVED** | Computed by the backend from observed values. | Operating state (`NORMAL`/`DEGRADED`/`CRITICAL`), fleet counts, health trends |
| **PREDICTED** | Model output. Rendered in violet; always carries model version and freshness. | `failureRisk`, `anomalyScore`, `rulEstimate`, attribution factors |
| **SYNTHETIC** | Produced by the simulator. Disclosed, not hidden. | The whole feed; `SYNTHETIC FEED` header chip; `dataBasis` in the status strip |
| **SIMULATED** | A what-if result. Changes nothing. | `POST /simulation/run` outputs, Scenario Lab projections |
| **UNAVAILABLE** | The backend could not supply it. Shown as unavailable, **never as a confident 0**. | Missing sensors, absent ML factors, unreachable panels |

Three rules the UI enforces:

1. **Unavailability is not zero.** A sensor the backend omits renders as
   unavailable, not `0`, because a confident zero is a fabricated measurement.
2. **Model output is never presented as measurement.** Violet is reserved for
   model output; a high risk value is violet, while the *machine state* is what
   turns red. Conflating them is the single most misleading thing a predictive
   maintenance UI can do.
3. **Severity and lifecycle are orthogonal axes.** An alert's severity is a
   colour; its lifecycle state is carried by weight and treatment, never by a
   second competing colour.

## 4. Telemetry: the two paths into the UI

```text
                 ┌─ high frequency ─► STOMP /topic/telemetry.updated
simulator ─┐     │                     validate → dedupe → order → coalesce
           ├─► backend twin          → ONE dispatch per animation frame
           │     │                   → useTelemetryStore (bounded, watched only)
           │     └─ low frequency ──► GET /machines/{id}/telemetry?limit=120
           │                         → TanStack Query → chart (authority)
           └─ POST /api/v1/telemetry/ingest
```

The realtime path is **low latency**; the REST path is the **authority**. If the
socket drops, the console keeps polling and simply gets slightly staler, and the
header says `STALE` or `DEGRADED` with a reason. It never silently shows
plausible-looking wrong numbers.

Backpressure / staleness rules (server-side, `application.yml`):

- Readings older than `forgesense.telemetry.maxStaleness` (default 60 s) are
  rejected, so a replay cannot flood the twin.
- Out-of-range physical values are rejected or clamped by the normalizer.
- No telemetry for a machine beyond `forgesense.machine.offlineAfter`
  (default 30 s) → connectivity `STALE`/`OFFLINE`.
- Per-machine ordering is preserved (keyed by `machineId`); cross-machine order
  is not assumed. The client sorts each flushed batch by envelope `sequence`.

## 5. Why every risk currently reads `0.060%`

All 18 assets report `failureRisk` exactly `0.0006`, which formats as `0.060%`.
This was investigated rather than assumed, and it is **genuine model output**:

| Test | Result | Rules out |
|---|---|---|
| Raw JSON precision | `"failureRisk":0.0006` | rounding, truncation |
| `anomalyScore` in the *same response* | 8+ distinct values (0.0, 0.9993, 0.0585, 0.0076, 0.0044, 0.0035, 0.0029, 0.0021, 0.0013, 0.0011, 0.0003, 0.0001) | adapter collapsing values |
| `healthScore` in the same response | 99.9 ×16, ~65–70 ×2 | shared state |
| `modelVersion` / `modelMode` | `failure-risk-v2` / `MODEL` ×18 | heuristic fallback |
| `formatProbability(0.00065)` | `0.065%` | formatter merging distinct values |
| Elevated asset after injection | `0.0585` — a 97× increase | saturation of the model itself |

**The values are preserved exactly as the model produces them.** No spread was
invented, because manufacturing variation in a safety-adjacent number would be
worse than an honest flat line. `failure-risk-v2` is a coarse classifier that
saturates near zero for nominal assets and only moves meaningfully once a
signal is clearly present.

A regression test (`test/format.test.ts`) pins the formatter's precision so a
future "simplify the number" change cannot quietly begin merging genuinely
distinct risks. The Command Center risk panel explains the saturation to the
operator rather than hiding it.
