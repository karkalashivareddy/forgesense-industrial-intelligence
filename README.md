## Data & ML validity boundary

**Every telemetry value and model training sample is synthetic.** The
repository's generator creates the data used to train and evaluate the models:

```text
simulator and machine profiles
  → generated synthetic telemetry and training samples
    → held-out synthetic evaluation
      → inference on simulator-generated telemetry
```

Previous metric values used a random row split and are withdrawn because rows
from the same synthetic machine trajectory could appear in both partitions.
Training now evaluates on a deterministic 20% group holdout of complete
synthetic machine trajectories and records ROC AUC, PR AUC, thresholded
precision/recall/F1, confusion matrix, class balance, a majority-class baseline,
RUL MAE/RMSE in simulator steps, and held-out group/sample counts. The latest
generated evaluation was on 2026-10-09 using 8 held-out trajectories (7,200
rows, 926 failure-risk positives; 12.86%):

| Evaluation | Result | Interpretation |
|---|---:|---|
| Anomaly ROC AUC / PR AUC | 0.9037 / 0.8729 | threshold 0.009576; precision 0.8654, recall 0.7466; 26.19% anomaly prevalence |
| Failure-risk ROC AUC / PR AUC | 0.9976 / 0.9843 | threshold 0.5; precision 0.9190, recall 0.9309, F1 0.9249; Brier 0.013485 |
| Failure-risk accuracy | 0.9806 | majority-class baseline 0.8714; confusion matrix `[[6198, 76], [64, 862]]` |
| RUL MAE / RMSE | 10.163 / 13.603 steps | failure-risk-positive held-out samples |

These are results on generated held-out machines only. Even a valid held-out
synthetic result does **not** establish real-world industrial predictive
validity.
The models were trained on synthetic simulator data, no real plant telemetry
or failure history is included, and the system does not control physical
machines.

The model artifacts and evaluation report are generated rather than committed;
see [docs/ML_PROVENANCE.md](docs/ML_PROVENANCE.md) for the current method and
reproduction command.

For a production deployment, this project would still need a real OPC UA or
MQTT ingestion path with source provenance, identity through an OIDC/SAML
provider, time-series storage, a model registry and drift monitoring, real
failure data, and RUL calibration against measured outcomes. These are future
requirements, not implemented features.

## What this is

ForgeSense is an industrial intelligence console for maintenance and reliability
teams. It consolidates condition monitoring, anomaly detection, failure-risk
estimation and attribution into a single operator workspace, anchored to a
spatial model of the plant so a system-level picture and a single-sensor reading
are one click apart.

The workflow is built around triage: rank by risk, open the driver, read the
sensor, decide.

## What it deliberately does not do

This is the most important section in this README.

- **It does not connect to equipment.** There is no OPC-UA client, no MQTT
  client, and no fieldbus driver anywhere in the codebase.
- **It cannot control machinery.** No write path exists to any device. The
  simulation layer injects faults into a synthetic feed; it does not actuate
  anything.
- **It is not synchronized with a real plant.** The digital twin is a
  visualization of simulated state, not a live model of physical equipment.
  There is no PLC, SCADA, MES or historian integration.
- **Model output is decision support, not an authoritative instruction.**
  Failure risk, anomaly score and remaining-useful-life are estimates. They are
  not guarantees, not calibrated probabilities, and not safety automation.
- **Estimated remaining degradation is expressed in simulator steps, never hours or days.**

Telemetry is synthetic, generated by a simulator in this repository.

## Product capabilities

| Capability | Description |
|---|---|
| Asset Intelligence | Per-asset health, risk and remaining-useful-life, each labelled with its data basis |
| Predictive Risk | Per-asset failure-risk estimate with model version and inference mode always visible |
| Anomaly Detection | Isolation-forest anomaly scoring, with a labelled heuristic fallback |
| Attribution | Signed per-sensor contribution to model output via baseline perturbation — not SHAP |
| Digital Twin | 3D factory hall with per-asset state, zone grouping and camera control |
| Telemetry Stream | Authenticated STOMP-over-WebSocket streams simulator output with sequencing and snapshot reconciliation; it is not a real sensor feed |
| Scenario Simulation | Engineer-gated fault injection into the synthetic feed, with recovery |
| Engineer Controls | Role-gated scenario and factory-reset controls, enforced server-side |
| Analytics | Fleet health distribution, risk scatter and event frequency |
| Maintenance & Alerts | Work records and alert lifecycle with acknowledgement |

REST carries the authoritative snapshot; STOMP carries updates. The console
keeps a REST poll as a reconciliation path, so a dropped socket degrades to
staleness rather than divergence.

The `dev` profile runs entirely in-process — embedded H2, in-process event bus,
in-memory cache — so the system boots with one command. PostgreSQL, Redis and
Kafka are used by the Docker Compose topology.

## Application surfaces

Twelve workspaces, all lazily loaded: **Command Center**, **Fleet**,
**Telemetry**, **Predictions**, **Anomalies**, **Analytics**, **Alerts**,
**Maintenance**, **Scenario Lab**, **Event Stream**, **Factory Twin**,
**System**.

## Predictive intelligence

The ML service produces anomaly scores, failure-risk estimates and
baseline-perturbation attribution. Artifacts are generated deterministically
from `config/machine_profiles.json` and validated by hash; see
[ML_PROVENANCE.md](docs/ML_PROVENANCE.md).

When the service is unreachable the backend falls back to a deterministic
heuristic scorer. That fallback is **not** ML inference, and the product says so:
the mode reads `HEURISTIC`, the model version reads `heuristic-v2`, and a
persistent banner tells the operator every value is indicative only. The
fallback scores against each asset's own machine-type profile, so a healthy
asset is not reported as an anomaly.

Attribution is labelled `BASELINE_PERTURBATION`. This is **not** SHAP, and the
console does not describe it as such.

## Digital twin

The twin is a modelled representation of a simulated plant, not a surveyed
model and not a live one. It renders a bounded factory hall — structural
columns, roof beams, aisles, transfer conveyors, overhead services and
equipment pads — with assets placed by zone. Machine assemblies are
representative geometry; status is carried by colour, indicators and selection.

Asset state in the twin is derived from the same live snapshot as every other
workspace, so it cannot disagree with the rest of the console.

## Security and roles

Three cumulative roles: `operator`, `engineer`, `admin`. Control-plane
endpoints are protected server-side with `@PreAuthorize`; the frontend hides
what an operator cannot use, but the backend is authoritative. The JWT is held
in `sessionStorage`. No real credential is committed, and CI fails the build on
a tracked credential default. See [SECURITY.md](SECURITY.md).

## Local development

Prerequisites: Java 25, Node 20+, Python 3.13.

```bash
# Backend — dev profile needs no external services
cd backend && ./mvnw spring-boot:run          # http://localhost:8080

# ML service — optional; the backend falls back to heuristics without it
cd ml-service && python -m venv .venv
.venv/Scripts/pip install -r requirements.txt
.venv/Scripts/python -m uvicorn app.main:app --port 8001

# Console
cd frontend && npm ci && npm run dev          # http://localhost:5173
```

Sign in with a seeded account (`operator` / `engineer` / `admin`); the password
comes from `FORGESENSE_DEV_PASSWORD`.

Container topology, which is where PostgreSQL, Redis and Kafka are real:

```bash
cp .env.example .env      # then set the four required secrets, see docs/DEPLOYMENT.md
docker compose up --build
```

The stack will not start until `POSTGRES_PASSWORD`,
`FORGESENSE_SECURITY_JWT_SECRET`, `FORGESENSE_DEV_PASSWORD`, and
`GRAFANA_ADMIN_PASSWORD` are set: Compose reads each with the `:?` form rather
than falling back to a committed default.

## Known limitations

- **Synthetic telemetry.** ForgeSense does not ingest physical sensor streams.
- **No equipment control.** No command path to any device.
- **No plant integration.** The twin is not synchronized with real equipment.
- **Model output is indicative**, not authoritative, and carries no guarantee.
- **Simulation is not a control system.** Scenario injection alters the
  synthetic feed only.
- **Single-node backend.** No load, failover or high-availability testing has
  been performed.
